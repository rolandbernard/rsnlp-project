
This section of the report discusses the methodology used for running the experimental evaluation. It follows a detailed description of the game rules, the used evaluation metrics, and some general information about the experimental setup.


\subsection{The Game}

\subsubsection{Core Mechanics}

The DoND game is a two-player, turn-based dialogue game designed to simulate a multi-issue bargaining scenario. \Cref{fig:example_dialogue} shows an example of a successfully played episode of the game. The core mechanics of the game are as follows.

\paragraph{Item Pool}
At the start of each game, players are presented with a shared set of items, consisting of several types and quantities, e.g., a possible set might be \textit{3 books, 2 hats, 1 ball}. 

\paragraph{Value Functions}
In addition to the shared set of items, each player is also secretly given a different private value function, mapping each item type to a non-negative integer indicating how much the player values that specific type. This value is then the number of points the player will receive for each unit of that type. The fact that the two players value functions are different creates the central conflict in the game. An example of such a value function might be \textit{book: 0, hat: 2, ball: 6}.

\paragraph{Negotiation}
After having received the initial prompt from the game master, containing the rules of the game, the shared set of items, and the players respective set of items, players are able to exchange free-form natural language messages. These messages are transmitted directly between them and can be in any format, provided they do not contain the special proposal syntax. This enables them to engage in negotiation about how to divide the items, with the goal of reaching an agreement.

\paragraph{Proposal}
At any point during the conversation, or once prompted to by the game master after a turn limit is reached, the players can make a secret proposal using a specific syntax, e.g., \textit{[Proposal: 2 books, 1 hat]}. Once one player has made a proposal, the game master instructs the other player to also make a proposal, crucially however, without revealing the content of the first proposal.

\paragraph{Outcome}
After both proposals are submitted, the game can end in either of two outcomes. Either the proposals are compatible, i.e., there are enough items to satisfy both proposals, or the proposals are conflicting. In case of compatible proposals, each player is awarded points based on total value of items they requested, according to their private value function. Should the proposals be conflicting, however, both players receive zero points.

The game master strictly enforces the rules. If a player fails to follow instructions, e.g., not making a proposal when asked, submitting a malformed proposal, or requesting items that do not exist, the game is immediately aborted. Unlike in \cite{liao2024efficacy} there is no re-prompting on errors, making rule adherence a critical component of successful play.

\subsubsection{Game Modes}

In order to potentially test different aspects of strategic reasoning, the \inlinecode{clemgame} implemented for this project also includes the three different game modes presented in \cite{liao2024efficacy}. The initial prompt given to the players is identical across modes, except for the final rule which specifies the optimization objective to the players.

\paragraph{Semi-Competitive}
In the semi-competitive setting, players are asked to maximize their own score. This is the standard negotiation setting, and it requires players to balance cooperation, to avoid zero-point conflicts, with competition, to maximize their individual share.

\paragraph{Cooperative}
For the cooperative setting of the game, players are asked to maximize the sum of their score and the score of the other player. This transforms the game into a purely cooperative task, where the optimal strategy is to identify for each item which player values it the most. In this setting two rational agents should always achieve the maximum score, assuming they are able to communicate and reason about the preferences perfectly.

\paragraph{Competitive}
In the competitive setting the game is transformed into a zero-sum game. To achieve this, each player is instructed to maximize the difference between their score and the score of the opposing player. This creates a strictly competitive, zero-sum game where for one player to gain points the other must necessarily loss them.


\subsubsection{Instance Generation}

The game instances for the evaluation were generated programmatically, as is standard within the \inlinecode{clembench} framework. This ensures a wide variety for possible initial conditions and somewhat controlled difficulty.

Each instance was generated with a maximum turn limit of 5, i.e., each player can send at most 5 messages to the other player before being forced to make a proposal. Furthermore, each game instance features a random set of between 3 and 5 different item types, differing from \cite{liao2024efficacy} and \cite{lewis2017deal} where the number of item types was fixed to 3. The item types for each game have been randomly sampled from a predefined list of 100 common nouns. The total number of items was set to between 5 and 8, and randomly distributed among the item types. Finally, a random value function of non-negative integers for all item types was generated for each player.

The value functions were generated subject to the same constraints as in previous work on DoND \cite{liao2024efficacy,lewis2017deal}.
\begin{enumerate*}
    \item The maximum value a single player can achieve by receiving all the items in the game instance is exactly 10.
    \item Every item in the game instance has a non-zero value to at least one of the two players.
    \item There exists at least one item that has a non-zero value to both players.
\end{enumerate*}
These constraints are crucial for creating meaningful negotiation scenarios. The fixed maximum score normalizes the game, while the two other constraints on the value function ensure that no items are irrelevant and that it is impossible for both players to simultaneously achieve their maximum score, thus forcing a compromise.


\subsection{Evaluation Metrics}

To assess the performance of LLMs in the DoND game, it is necessary to define the metrics by which they are scored. As is usual for the \inlinecode{clembench} framework, this is achieved through a combination of outcome-based and quality based metrics.

The first metric that will be considered is simply the percentage of played games, i.e., the percentage of games that have not been aborted due to rule violations. Games are aborted by the game master if either a malformed proposal is submitted, or no proposal is submitted after one is requested. This metric serves as the primary measure of the ability of the LLMs to follow the instructions.

Every \inlinecode{clemgame} should also define a metric specifying how well the game was played. For the cooperative game mode, assessing the quality of agreement is straightforward. Since both players try to optimize for the same total score of both players, it is simply possible to use the ratio between the achieved total score to the maximum possible total score for that game instance, $\mathit{Quality}_\mathit{coop} = \frac{\mathit{Score}_A + \mathit{Score}_B}{\max ( \mathit{Score}_A' + \mathit{Score}_B' )}$. This gives us a value between $0$ and $1$.

Evaluating the game in the semi-competitive setting is slightly more involved, as it requires finding a single score that jointly reflects the quality of the outcome for both players. For this, a metric based on Pareto efficiency has been used in this project. The score is defined as one minus the normalized maximum possible Pareto improvement, $\mathit{Quality}_\mathit{semi} = 1 - \frac{\mathit{Maximum Pareto Improvement}}{\max ( \mathit{Score}_i' )}$. The maximum possible Pareto improvement is the largest amount the score of one player could be increased without decreasing the score of the other. Normalization is performed by dividing by the maximum possible score a single player can obtain, resulting again in a value between $0$ and $1$.

As one additional metric for closer analysis of the game results this project employs also the percentage of games that end with Pareto optimal outcomes. An outcome is Pareto optimal if no players score can be increased without also decreasing the score of the other player. For the cooperative setting, an outcome is Pareto optimal if the players archives the maximum possible score. Note that in these cases the quality score will be $1$. 


\subsection{Experimental Setup}

All experiments were conducted using the \inlinecode{clembench} framework and its command-line tool, \inlinecode{clem}. In line with standard practice in similar dialogue game evaluations \cite{chalamalasetti-etal-2023-clembench,srivastava2022beyond} to ensure deterministic and comparable results, all LLM API calls were made with greedy sampling, i.e., temperature set to 0. Each model was evaluated using self-play for every instance, i.e., playing against a copy of itself.

\subsubsection{Game Instances}

The experiments focused only on the semi-competitive and cooperative game modes. The strictly competitive zero-sum setting was not evaluated. This decision was based on the inherent difficulty of evaluating zero-sum games in a self-play setting, a challenge reinforced by related work. For instance, \cite{liao2024efficacy} also mention that for the competitive version of the game, players must necessarily be evaluated by playing against a different model. This could be done eight by fixing one of the players to a specific model, which could however introduce possible bias, or by playing in a sort of tournament style, which would make the results more difficult to interpret. Given these challenges, this project has focused on the modes where outcomes are more clearly interpretable.

For the evaluation 50 unique game instances have been generated for each combination of the two game modes and three languages, English, German, and Italian. This resulted in a total of $50 \times 2 \times 3 = 300$ distinct experimental conditions. The core content of the instances, i.e., item types, counts, and value functions, was kept consistent across languages, with only the item names and prompt text being translated. All LLMs were evaluated on this same set of $300$ instances.
